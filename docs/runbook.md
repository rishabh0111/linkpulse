# LinkPulse — Runbook

One entry per alert, under the anchor the alert's `runbook` annotation carries
(`monitoring/prometheus/rules/linkpulse.yml`). Each entry says what the alert means, the
first three things to look at, what to do, what *not* to do, and what the chaos
experiment that induces this exact failure measured — so the numbers here are observed,
not guessed. Every command runs from the repository root inside the tool containers; on
a host with mise, `mise run <task>` is the same thing.

The evidence links go to `docs/evidence/chaos-N/timeline.md`, generated by the scripts in
`scripts/chaos/` from the runs described in `tracker.md`.

Conventions:

```
K="docker compose run --rm kubectl"          # the k3d cluster; set LINKPULSE_KUBECONFIG=/repo/.kube/burst for EKS
$K get pods -n linkpulse -o wide
docker compose run --rm smoke python3 scripts/observability-check.py --ingress http://k3d-linkpulse-serverlb
```

Dashboards (local): `http://grafana.localtest.me:8088` — *LinkPulse · Overview* for the
application, *LinkPulse · Kubernetes* for the cluster, *LinkPulse · Logs* for Loki.
Alertmanager: `http://alertmanager.localtest.me:8088`. All three also on `https://…:8443`
with the cluster CA (`mise run tls-ca`).

## high-error-rate

**LinkpulseHighErrorRate** — more than 5% of user requests returned 5xx over 2 minutes,
for 1 minute. Probe routes are excluded; 4xx is excluded. This is *users seeing errors*,
not a dependency being slow and not bad input.

**Meaning.** Something on the request path is failing closed: the GraphQL resolvers
cannot reach the table (a real store failure surfaces here as 500, deliberately — see
phase-2 bug 1 in the tracker), or the redirect lookup is failing. Throttling does *not*
produce this — click writes are asynchronous — so if this fires alongside
`LinkpulseClicksDropped`, the store is refusing *reads* too, which is a different and
worse problem than a hot key.

**Check.**
1. Which route: Overview → *5xx ratio* and *Requests by route*. `redirect` failing is the
   product down; `graphql` failing alone is the dashboard down.
2. Whether readiness agrees: if `LinkpulseNotReady` is also firing the pods know — go to
   [#not-ready](#not-ready). If it is not, the store answers the probe's `DescribeTable`
   but fails real calls: IAM (an item-level action denied), or a throttle on *reads*.
3. The logs: Logs → *Application: warnings and errors*, or
   `$K logs -n linkpulse -l app.kubernetes.io/name=linkpulse --tail=200 | grep -i error`.

**Act.** Fix the dependency; the application has nothing to restart. A deploy that
coincides with the spike is rolled back with `git revert` ([#rollout-stalled](#rollout-stalled)
has the mechanics), never with `kubectl rollout undo` — selfHeal reverts that within the
minute.

**Do not** scale up. More replicas against a failing store is more failing requests.

**Observed.** No experiment induces this directly, by design: experiments 1 and 3 both
assert a 5xx ratio of exactly zero while their failures are in progress
([chaos-1](evidence/chaos-1/timeline.md), [chaos-3](evidence/chaos-3/timeline.md) — the
latter shows 503 from the *ingress* with no endpoints, which the rule does not count
because no pod served it). The phase-7 outage test is where this rule first fired
wrongly, on probe traffic, and got its route exclusion.

## redirect-latency

**LinkpulseRedirectLatencyHigh** — redirect p99 above 250 ms for 2 minutes.

**Meaning.** The hot path is slow. The redirect does one eventually-consistent `GetItem`
and enqueues the click without waiting, so its latency is the store's read latency plus
the ingress. Nothing else is on that path.

**Check.**
1. Overview → *DynamoDB latency p99 by op*: if `GetItem` moved with the redirect, it is
   the store; if it did not, it is the pod (CPU: Kubernetes → *CPU*; there is no CPU
   limit, so throttling is not it) or the ingress.
2. The HPA: `$K get hpa -n linkpulse`. At `maxReplicas` with high CPU, the load has
   outgrown the ceiling; below it, the HPA should be scaling and the 300s scale-down
   window is the only thing to wait for.
3. Load shape: k6 running? A single hot link? On LocalStack a single key at 40/s produces
   p99 ≈ 250 ms with no fault at all (phase-9 finding 6): locally this alert measures
   DynamoDB Local before it measures anything else.

**Act.** On real DynamoDB a read-latency rise with no throttle is unusual; check the
CloudWatch exporter's `SuccessfulRequestLatency` on the burst. Locally, reduce the load.

**Do not** add a CPU limit to "protect" the pod: CFS throttling is a well-known cause of
exactly this symptom.

**Observed.** Baseline at 20/s on k3d: p50 12.9 ms, p95 105 ms, p99 180 ms
([k6 export](evidence/k6/baseline-k3d-localstack.json)). During experiment 1's throttle:
p99 25 ms against 21 ms clean ([chaos-1](evidence/chaos-1/timeline.md)) — throttling of
*writes* does not move this number, which is the point of the asynchronous design.

## target-down

**LinkpulseTargetDown** — a pod's `/metrics` has been unscrapeable for 2 minutes.

**Meaning.** Prometheus cannot reach the pod on port 8080. Either the pod is gone and
kube-state-metrics has not caught up (transient; resolves), or it is up and not
listening (a startup that hangs before the listener), or a NetworkPolicy would be in the
way if this cluster had any.

**Check.**
1. `$K get pods -n linkpulse -o wide` — does the pod exist, is it Running, which node.
2. Prometheus → Targets → `kubernetes-pods`: the scrape error text names the failure
   (connection refused vs timeout vs DNS).
3. If the node is NotReady, this is a symptom of [#node-lost](#node-lost).

**Act.** Usually nothing: it resolves when the pod is replaced. A pod Running for minutes
with `connection refused` on 8080 is a startup bug — `$K logs`.

**Observed.** Fires as collateral during experiments 4 and 5 for the pod being killed or
stranded; not asserted on because it is not the signal those experiments are about.

## clicks-dropped

**LinkpulseClicksDropped** — clicks are being discarded, at any rate above zero, for 30
seconds. The `reason` label says why: `throttled`, `queue_full`, `error`, `shutdown`.

**Meaning.** The click recorder could not write. Redirects are unaffected — the user got
their 302 — but the analytics for those clicks are gone; there is no retry queue beyond
the in-memory buffer. This is **the** experiment-1 alert: the user-visible symptom of a
hot partition is lost data, not latency, and an alert on latency alone sleeps through it.

**Check, by reason.**
- `throttled`: DynamoDB is refusing writes for capacity. Overview → *DynamoDB throttles*
  and *Click shards*. If `linkpulse_click_shards` is 1, the aggregate is on one key — the
  phase-4 verified mitigation is 16, set by `CLICK_SHARDS` in
  `k8s/manifests/base/config.env`. If shards are 16 and the table is at its 20 WCU ceiling
  (`ConsumedWriteCapacityUnits` on the burst), the table is simply full: the free tier is
  the ceiling and the honest fix is the one in the case study — accept the drop rate,
  or pay.
- `queue_full`: writes are not keeping up with redirects but are not being refused —
  latency on the write path. `CLICK_QUEUE_SIZE` (2048) and `CLICK_WORKERS` (8) are the
  knobs; the queue depth panel shows how close it runs.
- `error`: the write failed for a reason that is not capacity. Logs: `click write failed`.
  Usually IAM or the endpoint.
- `shutdown`: a pod was killed before its queue drained. `SHUTDOWN_GRACE` (15s) plus the
  5s preStop must fit inside `terminationGracePeriodSeconds` (40s); a burst of these on
  a rollout means it does not, or the node was lost (which is not graceful).

**Act.** For `throttled` with shards at 1: change `CLICK_SHARDS`, commit, let ArgoCD
roll it (the ConfigMap is hash-named, so the pods restart). For everything else, the
cause is upstream of the application.

**Do not** raise the table's capacity above the free 25/25 total (20/20 + 5/5 on GSI1)
without meaning to pay; the module's validation refuses it for that reason.

**Observed.** [chaos-1](evidence/chaos-1/timeline.md): first drop 10 s after the throttle
began, alert firing 65 s after (30 s `for` plus a scrape), 7.7 throttled calls/s and
~half the clicks lost while redirects continued at 20/s with p99 25 ms and zero 5xx;
resolved 20 s after drops returned to zero.

## dynamodb-throttled

**LinkpulseDynamoThrottled** — DynamoDB returned `ProvisionedThroughputExceededException`
for some operation, for 30 seconds. The `op` label says which.

**Meaning.** The table (20 WCU / 20 RCU, plus 5/5 on GSI1) is at its ceiling for that
operation class, or one partition is hot. On a table this small there is one partition,
so the two are the same thing; the per-partition limit (1000 WCU) is fifty times the
table's, which is why raising capacity would not be the fix even if it were free — see
`docs/data-model.md` §3.

**Check.** Which `op`: `UpdateItem`/`PutItem` is the click path and pairs with
[#clicks-dropped](#clicks-dropped); `GetItem` or `Query` throttling is reads, and the
redirect path will show it as latency and then errors — that is the serious case.

**Act.** As for clicks-dropped. Read throttling on the burst means a `Scan` is running
somewhere (`backup.py` paces itself under 10 RCU/s for exactly this reason; anything else
scanning is the finding).

**Observed.** Fires together with LinkpulseClicksDropped in
[chaos-1](evidence/chaos-1/timeline.md), same second.

## rollout-stalled

**LinkpulseRolloutStalled** — the Deployment reports `Progressing=False` with
`ProgressDeadlineExceeded`, for 1 minute. The new ReplicaSet is not becoming ready.

**Meaning.** A deploy shipped an image whose pods start (liveness passes) but never
serve (readiness fails), or cannot start at all. Because `maxUnavailable: 0`, the old
pods are all still serving — **there is no outage**, which is precisely why this alert
exists: nothing user-facing will tell you the deploy is stuck.

**Check.**
1. `$K get pods -n linkpulse` — the new pod, `0/1`, and its age.
2. `$K describe pod <new pod> -n linkpulse` — the readiness probe's last failure, or an
   image pull error, or a scheduling failure (resources, topology).
3. `$K get application linkpulse -n argocd` — Degraded, at which revision. That revision
   is the commit to revert.

**Act.** `git revert <that commit>` and push. ArgoCD syncs the revert, the bad ReplicaSet
scales to zero, the Deployment reports `NewReplicaSetAvailable`, the alert resolves.
Nobody touches the cluster.

**Do not** `kubectl rollout undo` or edit the image tag on the cluster: selfHeal reverts
it within the reconciliation interval, and the fix nobody wrote down is not a fix.

**Observed.** [chaos-2](evidence/chaos-2/timeline.md): ArgoCD synced the bad commit 84 s
after the push; the bad pod existed and never became Ready while both old pods served;
`ProgressDeadlineExceeded` at 204 s (the 120 s deadline plus sync); alert at 285 s
with the Application Degraded at the same moment; zero 5xx throughout. The revert was
synced 87 s after its push and the whole rollback took 109 s.

## not-ready

**LinkpulseNotReady** — a pod's own readiness has failed for 1 minute
(`linkpulse_ready == 0`, the process's view). **LinkpulseNoReadyPods** — Kubernetes has
no ready LinkPulse pod (`kube_pod_status_ready`, the kubelet's view); this one inhibits
the other so a full outage is one page.

**Meaning.** `/readyz` pings the store (`DescribeTable`) and fails if that fails. Every
pod failing at once is the dependency: DynamoDB unreachable, or the credentials it uses
revoked (on EKS, the IRSA role's policy detached — experiment 3's real-AWS form). One
pod failing alone is that pod's network. Liveness deliberately does not check the store,
so **the pods stay up**; they are out of the Service until the store returns and rejoin
on their own.

**Check.**
1. Both alerts or one? Both (NotReady inhibited, NoReadyPods firing) is the dependency.
2. `$K get endpoints linkpulse -n linkpulse` — empty means the ingress answers 503.
3. The store: locally `docker compose ps localstack` (paused? gone? — `mise run up` and
   `mise run tf-local-apply` bring it and the table back; the table is in-memory and does
   not survive a restart, `mise run restore` does). On AWS: `aws dynamodb describe-table`
   with the pod's identity, and the IAM role's attachments.
4. Logs: `readiness failed` lines name the error (`AccessDenied` vs a timeout).

**Act.** Restore the dependency. The pods recover without a restart — experiment 3 shows
5 s from unpause to two ready pods, and 0 restarts across the whole outage.

**Do not** restart or delete the pods. It changes nothing and resets the evidence.

**Observed.** [chaos-3](evidence/chaos-3/timeline.md): the process reported not-ready 17 s
after the store was paused; LinkpulseNotReady, the Kubernetes view and LinkpulseNoReadyPods
all landed at 92 s, with NotReady inhibited within the same poll; ingress 503; pods
Running with 0 restarts; 5 s to recover after unpause, alerts resolved 20 s later.

## crashloop

**LinkpulseCrashLooping** — a container has been in `CrashLoopBackOff` for 1 minute.

**Meaning.** The container keeps exiting and the kubelet is backing off (10 s, 20 s, 40 s,
80 s … capped at 5 m). `for: 1m` means at least four consecutive crashes have happened,
because the earlier backoffs are shorter than a minute. The last termination reason is
the diagnosis: `OOMKilled` → [#oomkilled](#oomkilled); `Error` with an exit code → the
process itself, read its last log lines.

**Check.**
1. `$K get pods -n linkpulse` — restarts and status.
2. `$K describe pod <pod> -n linkpulse | grep -A5 "Last State"` — reason and exit code.
3. `$K logs <pod> -n linkpulse --previous` — the previous incarnation's tail.

**Act.** A configuration that fails on start (an unparseable `CLICK_SHARDS`, a missing
table name) is a commit to revert. An OOM is below. The *other* replica is serving
throughout; the HPA keeps the count.

**Observed.** [chaos-4](evidence/chaos-4/timeline.md): five OOM kills on one pod, the
alert firing after the fifth (the 80 s backoff was the first to outlast the minute), the
other replica answering every check.

## oomkilled

**LinkpulseOOMKilled** — a container restarted and its last termination reason was
`OOMKilled`. **LinkpulseMemoryNearLimit** — a container's working set is above 85% of its
128Mi limit, for 1 minute: the warning before the kill.

**Meaning.** Memory is not compressible: there is no throttle, only the OOM killer. The
limit exists so that a leak takes the pod and not the node. This service sits at ~20 MB
at rest and does not grow under load (the GC keeps it flat) — so a genuine climb is a
leak, and the only leak the code has is the deliberate one behind
`LINKPULSE_ENABLE_DEBUG_LEAK` (local overlay only; a 404 on EKS).

**Check.**
1. Kubernetes → *Memory: working set vs limit* — the climb, and which pod.
2. Is `/debug/leak` enabled where it should not be? `$K get cm -n linkpulse -o yaml | grep LEAK`.
3. A rollout to a new image coinciding with the climb: revert it.

**Act.** A real leak is a code fix; the alert's job is to say which build introduced it.
Raising the limit buys time and the node's memory.

**Observed.** [chaos-4](evidence/chaos-4/timeline.md): 100 MB retained → working set above
85% within 15 s → NearLimit firing at 94 s → +40 MB → OOMKilled with restart 1 at 107 s
→ OOMKilled alert at 127 s. NearLimit resolved the moment the container restarted;
OOMKilled resolved five minutes after the last kill (`increase(...[5m])`, by design).

## node-lost

**KubeNodeNotReady** — a node's `Ready` condition is false for 1 minute.
**LinkpulseBelowMinReplicas** — fewer ready replicas than the HPA's `minReplicas`, for
30 seconds.

**Meaning.** A node stopped reporting. Its pods are marked not ready at once, but the
Deployment does not replace them until the taint-based eviction fires at
`tolerationSeconds` (300 s, the default) — so the service runs on the surviving replica
for about five minutes. That window is what BelowMinReplicas reports, and one replica on
another node is enough: that is what the topology spread constraint and two-node minimum
are for.

**Check.**
1. `$K get nodes` — which, and since when.
2. `$K get pods -n linkpulse -o wide` — one pod on the lost node (not ready, later
   `Terminating` and stuck until the node returns), one serving elsewhere.
3. What else was on that node: if Traefik, CoreDNS, Prometheus or kube-state-metrics were
   (this cluster runs them as single replicas with no PDB — phase-9 finding 4), the
   ingress or the observability is down too, and [#observability-is-down](#observability-is-down)
   applies.

**Act.** Bring the node back (`docker compose run --rm k3d node start <node>`; on EKS the
node group replaces it). The stranded pod is cleaned up by its kubelet on return. For a
*planned* removal use `kubectl drain`: the PodDisruptionBudget (`maxUnavailable: 1`)
allows one eviction at a time and the replacement is ready in seconds — experiment 5's
drain half.

**Do not** force-delete the stranded pod to "speed things up" unless the node is known
to be gone for good: a pod deleted from the API while its kubelet is unreachable may
still be running on the node, and for a service that drains a queue on shutdown that is
a double-write hazard.

**Observed.** [chaos-5](evidence/chaos-5/timeline.md): drain evicted the pod in 6 s with
the replacement Ready on another node 7 s in and no alert (the gap was under 30 s). The
stop: NotReady at 49 s, KubeNodeNotReady and BelowMinReplicas both at ~135 s, redirects
served throughout, 285 s below the minimum by Prometheus's samples until the replacement
was Ready, node Ready 7 s after start. (One rerun's timeline carries a 27-minute artefact
from a Docker Desktop clock jump; the tracker explains it.)

## graceful-shutdown

Not an alert; the behaviour every rollout, drain and scale-down relies on, and the
reason `cmd/server/main.go` handles SIGTERM.

When a pod is told to stop, three things happen concurrently: the endpoint is removed
from the Service, the `preStop` hook runs (a native 5 s `sleep` — the image has no
shell), and SIGTERM is delivered after it. The 5 s is the window in which Traefik and
kube-proxy still route to the pod; the process keeps serving through it, then on SIGTERM
stops accepting, drains the click queue (`SHUTDOWN_GRACE`, 15 s), and exits.
`terminationGracePeriodSeconds` is 40 s: 5 + 15 with room. If the drain does not finish,
the remainder is counted as `linkpulse_clicks_dropped_total{reason="shutdown"}` — the
one drop reason that is the platform's fault rather than the store's.

Check after any rollout: `sum(increase(linkpulse_clicks_dropped_total{reason="shutdown"}[10m]))`
should be zero. Experiment 2's rollback and experiment 5's drain both were.

## observability-is-down

If Grafana, Prometheus or Alertmanager do not answer, no alert above can fire, and the
absence of alerts means nothing. The check that proves the stack is observing:

```
docker compose run --rm smoke python3 scripts/observability-check.py --ingress http://k3d-linkpulse-serverlb
```

Twenty-nine assertions; every chaos task runs it last. The most likely causes on this
cluster: the node hosting the single-replica stack went away ([#node-lost](#node-lost)),
or Prometheus was rescheduled and its emptyDir history with it (retention is 2 days on
ephemeral storage locally; the aws overlay is the same — a persistent volume is a
deliberate non-goal for a 72-hour window, and the experiments render their panels to
PNG at the end of every run for exactly this reason).
